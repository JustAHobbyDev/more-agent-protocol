# AGENTS.md

This repository develops and distributes MORE — Manager / Owner / Reviewer / Executor.

## Current authority

For MORE-governed GitHub work:

- The latest valid handoff explicitly addressed to the acting role is operative instruction and authority.
- Historical instructions are context unless the active handoff incorporates them by exact reference.
- New authority does not erase unresolved evidence, failed verification, or observed technical facts.
- Repository state is technical truth.
- Verification outranks assertion.

## Repository roles

- **Manager** bounds and coordinates protocol work.
- **Owner** holds consequential project authority.
- **Reviewer** independently evaluates an exact candidate or protocol result.
- **Executor** performs the bounded task; Executor is not limited to coding.

Role combination is permitted where independence or authority separation is not required. Do not create ceremonial self-handoffs for trivial work.

## Protocol-development rules

- `SPEC.md` is the normative MORE v2 specification.
- `README.md`, examples, and case studies are explanatory and must not silently redefine the spec.
- Normative protocol changes require a concrete demonstrated failure, recurring friction, or adversarial case.
- Prefer clarifying an existing rule before adding a new mechanism.
- Narrow defects should produce narrow changes.
- Do not introduce parallel authority registries, session journals, command ledgers, or workflow databases unless repeated evidence proves GitHub insufficient.
- Reviewer findings are evidence, not votes.
- Reviewer approval and Owner authorization are candidate-bound.
- Unchanged valid evidence may be inherited; volatile evidence must be refreshed when current state matters.

## Working state

Before modifying files:

- inspect the governing issue or pull request;
- inspect existing repository state;
- preserve unrelated user or agent work;
- do not reset or delete unknown work merely to recreate a clean baseline.

## Pull requests

Specification changes should normally be developed through a branch and pull request linked to an issue.

A PR changing normative behavior should state:

- behavior changed;
- motivating failure/evidence;
- verification or adversarial case;
- compatibility impact;
- whether examples/case studies require updates.

## Current release status

The repository is developing **MORE v2.0.0-rc.1**.

Do not describe RC behavior as stable v2.0.0 until a stable release has been explicitly approved and published.
